3.2 Worker 是什么：和 Orchestrator 对比

OrchestratorWorker
数量1 个3 个实例：researcher、coder、writer
做什么理解人类的请求，拆成几步，决定调用哪个 Worker，最后汇报接到一个具体任务，自己动手完成
手里的工具call_<agent>、ask_human、finish（都是"指挥"类）真实工具（搜索、读写文件、运行 Python、git…）+ call_<agent>（可再委派）+ decline + read_group
谁写JIAN YiminLI Heyang

Worker 的 ReAct 循环（handle_task 里，反复"想一步 → 调一个工具 → 看结果"）：

  1. 先从记忆里召回相关经验，再把会话看板的文字放进 prompt。
  2. 判断任务是否超出自己的能力，是就 decline 拒绝，不开始做。
  3. 循环最多 12 步，每步由 LLM 决定调用哪个工具。
  4. 遇到需要批准的工具（删除文件、git push）先问人类；同一工具连续失败 2 次也向人类求助。
  5. 做完后返回 TaskResult：摘要，加上写过哪些文件和提交 hash（由代码根据工具调用记录自动补全）。
  6. 把这次的经验写进记忆；失败时异步反思一次。

立刻回答每个请求（answer 直接返回默认答案），不读键盘。它可以直接用 handle_incoming，不用自己拼 HITL_RESPONSE。

嵌套 = "继承自"。CliHumanIO 和 AutoResponder 共用外层 HumanIO 的方法，所以"收到请求 → 回答 → 发回 HITL_RESPONSE"这条路只写了一遍。

4.3 请求怎么回答：/reply

agent 请求批准时，CLI 要在不阻塞输入和显示的前提下等人类回答，并且支持同时有好几个请求。关键还是那张"回执条"：answer 登记一张，/reply 填上它。

写很简单：往文件末尾追加一行。有意思的是读：同一个任务可以写两次（先记失败，等反思出教训再补一次），读的时候后写的算数；坏掉的行跳过。

6.3 recall：怎么找出相关的经验

没有向量数据库，用最朴素的关键词重合：把查询和每条记录都拆成关键词，数重合的个数当分数。对中文，拆成相邻两个字（"爬虫脚本" → 爬虫、虫脚、脚本）。

6.4 profile：能力档案怎么来

纯统计：最近 20 条里每种类型成功了几个，加上最近几次失败的教训，拼成一两句话。Orchestrator 把它读进工具描述，LLM 选人时就能参考。
