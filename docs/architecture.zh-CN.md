## 1. 概览

用户用一份 Markdown 文件描述一个**团队**：有谁，每个人负责什么。角色的内容一点也没有写死在代码里。
人类在群聊或私聊里与团队交流。每个请求由团队里的**一位成员牵头**：它弄清需求，拆分工作，委派给队友，
检查结果并汇报。每个 agent 有自己的工作区、自己的工具和自己的持久记忆。

```
  人类 ───────────────▶  消息总线（群聊、私聊）
                            │  每条消息都会被观察者看到：
                            │    Router（结果、人类的回答）   SessionBoard（共享进展）
                            │    RequestTracker（新请求）     Transcript（完整对话）
                            ▼
  RequestTracker ── LeadSelector ──▶  牵头者（一个 WorkerAgent）
   （记账，不调 LLM）  （一次 LLM 调用，       │
                       有缓存）               ├─ ask_human ──▶ 人类
                                              ├─ call_<队友> ──▶ Router.dispatch ──▶ 队友（WorkerAgent）
                                              └─ 它自己的工具 ──▶ 它的沙箱（私有工作区）
```

设计原则：

1. **协调由团队成员完成，不是由隐藏的调度器完成。** LLM 周围的事（路由、限制、状态、文件、记账）都是确定性的普通代码。
2. **委派只有一条代码路径。** 无论谁委派、在哪里委派，都经过 `Router.dispatch`，限制、状态、文件交接和统计无法被绕开。
3. **失败是观察结果，不是异常。** 工具失败、调用被拒、队友失败，都会作为结果返回给发起调用的 LLM，由它决定怎么办，不会让运行崩溃。
4. **评测要用的数字都由代码记录**，不取自 LLM 对自己的描述。

## 3. 通信拓扑

- **群聊**（`group:main`）：人类和所有 agent 都是成员。任务交接、结果、向人类的提问和回答都是公开的，
  所以人类能看到谁请谁做了什么。
- **私聊**（`dm:<human>:<agent>`）：人类可以只和一个 agent 说话，由它自己执行任务（仍可以再委派）。
  私聊任务里发生的委派只留在那个私聊频道里。
- **寻址。** 一条消息会*送达*频道里的每个成员，但 agent 只对 `receiver` 是自己、或 `@` 到自己的消息*行动*，
  所以收消息不花 LLM 调用。人类发的、没有 @ 任何人的消息是一个**请求**，由 `RequestTracker` 处理；
  `@dev ...` 直接把任务交给 `dev`；`/dm dev ...` 开启私聊。
- **消息类型**：`CHAT`、`TASK_ASSIGN`、`TASK_RESULT`、`HITL_REQUEST`、`HITL_RESPONSE`、`STATUS`。
  载荷都是普通 JSON，所以每条消息都可以记录和重放。
- **观察者。** 总线在投递前同步调用已注册的观察者：Router 用它完成等待中的委派和人类提问，看板用它记录进展，
  `RequestTracker` 用它发现新请求，`Transcript` 用它写对话。

## 4. 路由与委派

### 4.1 从人类的消息到牵头者

| 人类说 | 发生什么 |
|---|---|
| 群里的普通文字 | 一个**请求**：开一个新 root（`R1`、`R2` ……），选出牵头者。如果已有请求在运行，这段文字是对它的**补充** |
| `@dev ...` 或 `/dm dev ...` | 给 `dev` 的直接任务（有自己的 root）；`dev` 牵头，仍可委派 |
| `/status`、`/cancel` | 由 `RequestTracker` 根据状态表回答，不调 LLM |

### 4.2 选牵头者

`LeadSelector.choose(session, request)` 用一个工具 `choose_lead` 做**一次 LLM 调用**。提示词列出每位成员的
agent id、角色名和提示词，请它选出最适合*协调*这个请求的人（负责理解目标、做决定的人，而不是只负责执行其中一部分的人）。之后：

- 答案**按会话缓存**，所以同一场对话里的后续请求（Task 1 之后的 Task 2）沿用牵头者，不再调用；
- 如果调用失败、答案不是团队成员、或模型没有调用工具，就由**团队里的第一位成员**牵头，这个兜底不缓存（下一个请求会重新问）；
- 只有一位成员的团队不需要调用。

### 4.3 牵头者做什么

牵头者就是一个普通的 `WorkerAgent`，它的任务没有父任务。它与其他成员的区别只在预算
（`max_lead_steps` 40 步、`lead_timeout_s` 2400 秒、最多 `max_lead_delegations` 16 次委派）和一小段额外指示：
弄清请求，不清楚就问人类，拆分工作，委派，让队友复核重要结果并退回修改，结果好了才结束，最后写一段人类能读懂的回答。
它的工具是团队的 `call_<队友>`、`ask_human` 和它自己的工具。它最后的回答就是人类读到的话，它列出的文件就是交付物。

它的预算和什么时候停见 [4.5](#45-预算并行与停止)。

### 4.4 委派（`Router.dispatch`）

每个 `call_<队友>` 都变成 `Router.dispatch(requester, target, goal, context, files, parent, ...)`：

1. **先检查限制**；被拒绝的调用也会登记（状态 `FAILED`，错误 `refused: ...`），所以它会出现在 `/status` 和统计里，
   并作为普通的失败结果回到调用方。

   | 限制 | 默认 | 何时拒绝 |
   |---|---:|---|
   | 未知目标 | | 目标不是群里的成员 |
   | 循环 | | 目标已在委派链上（包括调用者自己） |
   | 深度 | 2 | 牵头者之下的委派链会超过 `max_delegation_depth` |
   | 每个任务的委派次数 | 2（牵头者 16） | 某个 worker 的任务已经委派了这么多次 |
   | 同一目标重试 | 2 | 同一个 root 里同一个目标已在同一个 agent 上试过 3 次；被拒绝（decline）的不算 |
   | 已取消 | | 这个 root 已被取消 |

2. 任务在 `StateTable` 里**登记**，它的 `files` 从请求者的工作区（或产出这些文件的 agent 的工作区，先在本 root 里找，
   再在同一会话更早的 root 里找）**复制**到目标的 `inbox/`。
3. 发出 `TASK_ASSIGN`（在群里，或任务所属的私聊频道里）。
4. Router **等待**对应的 `TASK_RESULT`，有时限（`subtask_timeout_s` 900 秒；整个请求用 `lead_timeout_s`）。
   **等待人类的时间不计入。**

目标在自己的 ReAct 循环里执行任务。它可以在第一步**拒绝**超出自己能力的任务并建议更合适的成员；拒绝会连同建议一起返回给调用方，
它不算失败，调用方可以改派。队友也可以在上述限制内继续委派。成员在同一次回复里连续发出的多个委派是并行执行的，见 [4.5](#45-预算并行与停止)。

### 4.5 预算、并行与停止

**上限。** 全部是 `Settings`（`mas/config.py`）的字段。

| 上限 | 默认值 | 限制的是什么 |
|---|---:|---|
| `max_worker_steps` | 30 | 一个成员完成一个任务的 ReAct 步数（模型调用次数） |
| `max_lead_steps` | 40 | 同上，针对一个请求的牵头者 |
| `subtask_timeout_s` | 900 秒 | 一个被委派的任务；等待人类的时间不计 |
| `lead_timeout_s` | 2400 秒 | 一个完整的请求 |
| `max_lead_delegations` | 16 | 一个请求的牵头者可以委派的次数 |
| `max_delegations_per_task` | 2 | 其他成员为一个任务可以委派的次数 |
| `max_delegation_depth` | 2 | 委派在牵头者之下最多嵌套几层 |
| `max_retries_same_goal` | 2 | 同一个请求里同一目标在同一个 agent 上的重试次数 |

**并行委派。** 成员在同一次回复里连续发出的多个委派会**同时执行**：发给不同队友的并行，发给同一位队友的一个接一个（它们共用那位队友的工作区）。
结果按发出的顺序返回；其中一个让任务结束（被取消、超时）时，其余的一并停止。回复里夹着的其他工具调用仍保持原来的顺序，因为后面的委派可能依赖前面写的文件。
需要另一个结果的活放到下一次回复里再发，提示词里也这样说明。成员等待队友的时间记录的是等待的挂钟时间，不是各个任务时间的总和。

**成员什么时候停。** 成员不调用工具、直接给出回答时，任务就结束。步数上限只是封顶，找到所需信息的成员会被要求写出结果并结束。
有几个提醒推动它提前停下，而不是研究到封顶。它们是对话里的建议，不是规则，可以一起关掉（`early_stop_nudges`：`EARLY_STOP_NUDGES=0`，或 `python -m mas.eval --early-stop off`），用来度量它们改变了什么。

| 提醒 | 何时 | 成员看到的 |
|---|---|---|
| 重复提示 | 成功的搜索或抓取被重复 | "和第 N 步是同一个调用，结果一样：用已有的"（调用照常执行；搜索和抓取有缓存，不花时间） |
| 研究提醒 | 搜索或抓取满 `research_note_after`（12）次，之后每 `research_note_every`（6）次 | "除非还缺某个具体事实，否则别再查了，把已有的写出来" |
| 进度检查，worker | 用掉一半步数，还没写出任何文件 | "把已有的写下来并结束，或说明还缺什么" |
| 进度检查，牵头者 | 用掉一半步数，整个请求里还没有任何文件 | "确保交付物正在被写：先安排人去写，再做更多研究和审阅" |

失败的调用从不算"做过"，所以随时可以重试。兜底不能关：剩 3 步时成员会被告知，最后一步不给工具，它必须用已有的内容作答并说明缺什么，而不是以"步数用尽"收场。

### 4.6 结束一个请求

牵头者的任务返回后，`RequestTracker`：

- 把交付物（牵头者列出的文件；没列就是这个 root 里所有成功任务写的文件）从写它们的 agent 的工作区复制到
  `data/output/<root>-<时间>/`（重名的加 `<agent>_` 前缀；列出但不存在的文件会被报告，不会被藏起来）；
- 记录一个 `RootOutcome`（是否成功、失败模式、耗时、牵头者、交付物、输出目录）；
- **以牵头者的名义**发出最终回复，载荷里有评测可读的结构化信息：
  `{"final": true, "root_id", "success", "failure_mode", "rounds", "duration", "lead", "deliverables", "output_dir"}`。

牵头者失败、超时或崩溃时仍然会有回复，并带上失败模式（`llm_format`、`tool_error`、`timeout`、`max_steps`、`wrong_output`、`crash`）。
被取消的请求没有回复（`/cancel` 已经说明了取消了什么）。

### 4.7 取消

`/cancel` 把这个 root 下所有未结束的任务标为已取消，唤醒所有等待它的东西（委派、人类提问），并拒绝之后的调用。
Router 无法停止正在运行的 agent，所以**worker 在每一步之前、以及执行任何需要批准的工具之前都要检查是否已被取消**；
返回"cancelled"的人类提问一律当作"停止"，绝不当作同意。

## 5. 人在回路

agent 在三种情况下会暂停并询问人类；提问都出现在请求开始的那个聊天里，并带编号（`h1`、`h2` ……），可以同时有多个未答的：

| 情况 | 类型 | 谁问 |
|---|---|---|
| 请求或某一步有歧义 | `clarify` | 任何成员，用 `ask_human` 工具（主要是牵头者） |
| 执行标有 `requires_approval` 的工具之前（`git`、`delete_file`）；删除本任务自己写的文件（比如临时脚本）不需要批准 | `approval` | worker，自动 |
| 同一个工具连续失败两次 | `advice` | worker，自动 |

人类用 `/reply <id> <答案>` 回答（只有一个未答问题时可只写 `/reply <答案>`）。等待人类时任务的计时暂停。命令行是 `CliHumanIO`；
无人值守时由 `AutoResponder` 按问题类型用固定的默认答案回答（这是一个局限，见 §13）。请求运行期间人类发的消息会记在看板上，
worker 在下一步读到。

## 6. 记忆与进化

**存储。** 每个 agent 有自己的文件 `data/memory/<agent_id>.jsonl`，每个任务一条 JSON 记录：目标、任务类型标签（由用到的工具得出）、
是否成功、总结，以及失败时的一句**教训**。文件每次使用时重新读取，所以记忆在重启后仍然存在：用同一个数据目录开始的新运行，
会带着 agent 之前学到的东西。我们用两次完整的程序运行验证了这一点（`tests/test_memory_across_sessions.py`）。

**从经验中学习。**

| 机制 | 做法 |
|---|---|
| 记录 | 任务结束时（被拒绝或被取消的除外）worker 写一条记录 |
| 反思 | **失败**之后，worker 在后台、不占用关键路径地问一次 LLM 要一条教训，并用带教训的记录替换原记录 |
| 召回 | 任务开始时，把最相关的 `memory_recall_k`（3）条记录放进提示词。相关度是关键词重合（目标和标签算两倍，总结和教训算一倍；中文按连续汉字匹配）；带教训的多算一分；同分取较新的 |
| 简介 | 取最近 20 条记录：每种任务类型的成功次数，加最近几次失败的教训，例如 `Recent performance: code 8/10 succeeded, search 1/2 succeeded. Known weak spots: ...` |

**记忆会改变分工。** 一位成员的简介会附在它的 `call_<成员>` 工具描述里，所以委派的人能看到每位队友最近表现如何、要避开什么。

**隔离。** 一个 agent 只读自己的文件；队友只能看到那段简短的简介。

**局限。** 记录里是目标、结果和教训，不是对话内容；召回基于关键词（没有向量检索）；教训只在失败之后产生。
这套机制在多次运行中是否真的提高了结果，由测试报告度量，这里不作假设。

## 7. 沙箱与工作区隔离

每个 agent 有一个私有目录 `workspaces/<agent>/`，和一个绑定在它上面的 `Sandbox` 对象。**工具从不直接碰文件系统或执行命令**，
一律通过沙箱，而沙箱会：

- 把每个路径**解析**到工作区根目录下，跟随符号链接，最终落在外面的一律拒绝（`PermissionError`）；在 Windows 上还会拒绝设备名和 NTFS 备用数据流；
- **以 UTF-8 写入并保持换行不变**；只删除文件；
- **执行命令**（`exec`）时以工作区为工作目录，有超时和指定的环境变量；工具给 LLM 看的输出会被截到 `tool_output_max_chars`（4000）；
  进程在独立的会话（POSIX）或结束时即杀的作业对象（Windows）里启动，所以超时或取消时整个进程树都会被杀掉；
- **只在 Router 要求时把文件导入 `inbox/`**：来源是另一个 agent 工作区里的文件，目的地必须在本工作区的 `inbox/` 之内，
  已存在的文件绝不覆盖（复制是独占的，所以并发导入不会互相覆盖）。

文件只能通过 Router 在 agent 之间流转，Router 在 `dispatch` 时复制。因此数据不会意外地在 agent 之间泄漏：
队友只有在委派者交给它时才能看到某个文件。

实际运行的是 `LocalSandbox`。它把各 agent 的文件分开，但**命令以宿主用户的权限执行**，所以它不是安全边界。
`DockerSandbox`（每个 agent 一个常驻容器，只挂载自己的工作区）是计划中更强的隔离，尚未实现。

## 8. 工具

| 工具 | 作用 | 说明 |
|---|---|---|
| `read_file`、`write_file`、`list_files` | 读取、创建或覆盖、列出 | 工作区内的相对路径 |
| `delete_file` | 删除文件 | 需要人类批准 |
| `run_python` | 在工作区里运行脚本或模块（`unittest`、`pytest`） | 有超时（默认 60 秒），返回输出和退出码 |
| `web_search` | 标题、链接和摘要 | 配了 key 用 Brave Search；否则、或 Brave 拒绝或不可用时，改用无 key 的应急搜索（`ddgs`，只调一次）：12 秒期限，连续失败 3 次后停手 30 秒并告诉成员别等它、继续往下做。真正的搜索 API 会取代它 |
| `fetch_url` | 抓取公开网页的文本 | 只限公开的 HTTP(S)：每一次重定向都会拒绝私有和混合地址；20 秒和 1 MiB 的限制；文本、HTML、JSON、XML |
| `git` | `init`、`clone`、`status`、`diff`、`add`、`commit`、`log`、`push` | 每次调用都需要人类批准；GitHub token 只通过 HTTPS 发给 github.com，不会出现在输出里 |

产出只用纯文本：文档是 `.md` 和 `.txt`（HTML 和代码文件也允许）。每个工具都返回 `ToolResult`（`ok`、给 LLM 看的文本、写入的文件、
提交号之类的引用），预期之内的失败不抛异常。工具写出的文件会自动成为任务的产物。

## 9. 共享上下文与对话记录

**会话看板。** 每个会话（群聊或一个私聊）有一块看板，由代码根据结构化消息维护，**从不让 LLM 做摘要**，所以文件名和 id 不会丢：
人类的原话、已完成的事（含文件和要点）、失败或被拒绝的事、人类的决定、还没做完的事，以及此前每个请求一行。
任务开始时它会在大小预算内注入 worker 的提示词，Task 2 就是这样看到 Task 1 的结果的。看板在一次运行内保存在内存里。

**对话记录。** 一个总线观察者把整场对话写到 `data/transcripts/<场景>-<时间>.md`：人类说了什么、谁牵头、谁把什么委派给谁、
团队问了什么、人类答了什么、每个结果、每个请求怎么结束，以及一张汇总表。每个请求结束时重写一次。把这个文件交给模型就能评分。

## 10. 评测

`python -m mas.eval <场景文件夹>`（`mas/eval/harness.py`）在全新的系统里依次跑每个场景的任务，由代码统计：**任务完成率**（请求，
以及牵头者委派的子任务）、每个请求的**执行时间**（均值、中位数、最大值）、失败模式计数和团队向人类提问的次数。
结果写成 `report.md` 和 `results.json`，并保留每次运行的对话记录和交付物。

- `--human llm`（默认）：由 `SimulatedHuman` 扮演提需求的人回答团队的澄清问题；`--human auto` 用 `AutoResponder` 的固定答案。
- `--judge`：让模型给每个任务的对话和交付物打分（`mas/eval/judge.py`），和课程的评分方式一致。
- `--repeat N --keep-memory`：同一场景保留记忆再跑，用来度量记忆有没有帮助。
- 没在时限内跑完的场景记为失败，不会卡住。

框架之外每个请求也都会记录：`RootOutcome`、最终回复的载荷和对话记录。`docs/report.md` 写明了到目前为止测过什么。

## 11. LLM 后端

课程允许的两个后端都使用 OpenAI 的 chat-completions 协议和 function calling：HKGAI（默认，`HKGAIClient`）和
DeepSeek（`DeepSeekClient`，即用 DeepSeek 默认值的同一个客户端），用 `LLM_PROVIDER` 或 `--llm` 选择。DeepSeek 默认被要求不思考（`DEEPSEEK_THINKING=off`）：agent 的每一步都是工具调用，思考会让每次调用更慢，
而且思考模型的推理文本必须随之后的每个请求一起发回去，否则接口会拒绝。客户端对超时、限流和服务端错误做指数退避重试并遵守
`Retry-After`，修复带围栏或带尾逗号的工具调用参数，校验每个响应，重试用尽后才返回 `LLMError`。不使用 OpenAI 和 Anthropic 的 API。
测试使用 `MockLLM`，一个脚本化的替身。

## 12. 配置与数据目录

所有上限都是 `Settings`（`mas/config.py`）的字段：步数上限（`max_worker_steps` 30、`max_lead_steps` 40）、时限（`subtask_timeout_s` 900、
`lead_timeout_s` 2400）、委派限制、记忆召回条数、沙箱后端、路径。密钥来自 `.env`。

```
workspaces/<agent>/        每个 agent 的私有文件，inbox/ 放别人交给它的文件
data/memory/<agent>.jsonl  每个 agent 的记忆
data/output/<root>-<时间>/ 每个请求的交付物
data/transcripts/          每次运行的对话
data/mas.log               日志（内部错误的堆栈）
```

## 13. 局限

- `LocalSandbox` 不是安全边界；Docker 沙箱尚未实现。
- 会话看板保存在内存里：程序重启后，各 agent 记得自己学到的东西（记忆），但不记得这场对话里之前的请求。
- 无人值守的 `AutoResponder` 对所有问题都给固定的默认答案，不能代替有真实偏好的人类（比如投资者的风险承受能力）。
- 无 key 的网络搜索只是应急方案：它依赖会限流或改版的第三方引擎，所以有些搜索会失败（在一个网络上的测试里 8 次有 2 次）。它被设计成失败只花几秒、不会拖住整个运行；要让研究可靠，靠的是真正的搜索 API（`SEARCH_API_KEY`）。
- 召回基于关键词，并且只从失败中产生教训。
- 还没有用真实模型在测试集上做过端到端评测（见报告）。
