**已修复的 Windows 耗时问题：** 修复前 `tests/test_agent_base.py` 的
`RunLoopTest.test_task_roundtrip` 断言 `r.duration > 0`，实测得到 `0.0`。
当时 `mas/agents/base.py` 用两次 `time.monotonic()` 相减计算耗时。本机
`time.get_clock_info('monotonic')` 显示实现为 `GetTickCount64()`、分辨率 `0.015625s`，
短任务可能在同一时钟刻度完成。按用户后续请求，内部起止计时改为 `time.perf_counter()`，
本机实现为 `QueryPerformanceCounter()`、分辨率 `1e-7s`。duration 仍为浮点秒，
仅在 Worker 未提供非零 duration 时补齐，不填造最小耗时、不加入 sleep。
Agent 的全部 14 个方法签名经静态比较与基线一致，TaskResult 源文件未改。

保留原有 `duration > 0` 断言，新增两项回归：粗时钟未前进时仍能记录 0.4ms 短任务；
Worker 自报的 2.5s duration 不被覆盖。两项同时检查返回值和 TASK_RESULT 消息中的 duration。
定向 Agent 回归 22 项全部通过，1.083 秒，实际命令为：

```powershell
python -u -c "import faulthandler, unittest; faulthandler.dump_traceback_later(30, exit=True); unittest.main(module=None, argv=['unittest', 'tests.test_agent_base', '-v'])"
```

**两项跳过：** workspace 符号链接越界与 inbox 符号链接重定向测试。
本机创建链接报 `WinError 1314`，缺少权限。需要在允许创建符号链接的环境补验。
POSIX 命令执行分支也尚未实测。

### 7. 无 key 搜索的两次修改

第一次真实运行里，`web_search` 平均 19 秒一次（共约 54 次，占了总时间的大半）。我先把它改成"同时问 bing、yahoo、google、duckduckgo，谁先有结果用谁"，并加了缓存。
第二次运行的控制台里出现大量警告：`bing - backends do not exist or are disabled ... Using 'auto'`。原来这个版本的 `ddgs`（9.16.1）里 bing 和 google 是被禁用的，
指名它们只会悄悄退回 `auto`。所以那次"并行问四个引擎"其实是两次 `auto` 加 yahoo 和 duckduckgo，请求重复，而我之前量出的"bing 3/5 成功、google 2/5"实际是 `auto` 的结果。
搜索能用，但配置和我写下的说明都不对。

现在改成最简单的形式：对 `ddgs` 只调一次 `auto`（库自己会并行问它的引擎），12 秒期限，连续失败 3 次后停手 30 秒并明确告诉成员"别等它，用 `fetch_url` 或写下已有的"；搜索和网页抓取都有缓存。
这是应急方案，等老师的搜索 API 到了会被取代。同一个网络上 8 个真实查询：6 个成功，平均 6.4 秒，最慢 9 秒（当时另一个评测正在同一个网络上运行，会加重限流）；失败的两个也在 9 秒内返回，并带着下一步怎么办的提示。

### 5. 过程中发现并修复的缺陷（有些是我们自己引入的）

1. **`import_file` 不覆盖，重发修订版会失败**（改动 3）。分析第三轮的对话记录时发现，这是比"牵头者忘了列文件"更深的原因。
2. **文件名检查不够**：第三轮最终签核的任务文字只提到中文版文件名，没提英文方案的文件名，所以只靠"任务文字里的文件名"抓不到旧版。后来加了"收件箱里已有同名旧副本就换成新版"。
3. **过期检测不等于评审干净**：见改动 5，第七轮 Task 1 仍有矛盾。
4. **评审退回在最后一步丢掉有效答案（我们自己引入）**：改动 10 的"交付物未评审就退回"在牵头者最后一步给出最终答案时也触发，把答案退回去，而这时已没有步数，请求以 `max_steps` 结束、回复为空，交付物其实不差（场景 1 Task 2 评分 8）。第八轮因此 2/4 完成。已修复（改动 11）。
5. **失败请求的交付物变成牵头者写过的所有文件**：场景 1 Task 2 在失败那次交付的是 `show_dash*.py` 这类临时脚本而不是 `roombook.html`。这是失败路径的副作用，正常路径不会这样。
6. **pytest 会把 `eval_results/` 下团队生成的测试文件也收集进来**：在项目根目录直接 `pytest` 会报收集错误，需要写成 `pytest tests`。
7. **评分员只看到每个交付文件的前 8000 个字符（评测框架自己的缺陷，第十轮之后才发现）**：`mas/eval/judge.py` 里 `MAX_FILE_CHARS = 8000`、单次总量 `MAX_FILES_CHARS = 30000`，对话只取最后 20000 字符。归档的 19 个任务输出里有 **17 个至少有一个交付文件只被评分员看到一部分**：HTML 幻灯片只看到 19% 到 41%（例如 41796 字符里的 8000 个），提案和报告 34% 到 62%。截断处还会加一个 `…(cut)` 标记，评分员把它当成了交付物的缺陷。**所以到目前为止所有评分，凡是长交付物，都是基于一份不完整的文件打的**（见 §8）。
8. **给人类的最终回复"放宽到 6000 字符"没有生效（我们自己的修复不完整）**：`worker.py` 里把牵头者的摘要上限设成 6000，但基类 `Agent.on_message`（`mas/agents/base.py` 第 106 行）在 `handle_task` 返回之后又把所有结果截到 `result_summary_max_chars`（1500）。第十轮场景 1 Task 2 的最终回复正好截在 1500 字符并以 `…` 结尾，评分员写"最终回复被截断"说的就是这个。要求清单里"未满足项"那一段是追加在摘要末尾的，回复一长就会被一起截掉。
9. **牵头者陷入"重复同一个补丁"的循环，并且声称修订已完成**：场景 3 Task 2 的牵头者用 Python 脚本给 42 KB 的幻灯片打补丁，同一个 12 KB 的补丁脚本（44 处替换）被写了 10 遍（`fix3.py` 到 `fix12.py` 逐字节相同），而最终交付的幻灯片里这 44 处**一处都没有生效**（旧文字全在、新文字一处没有），最终回复却说做了修订。见 §9 第 1 条。

### 8. 限制：这些数字不能说明什么

### 4. 查到的四个问题

**4.1 一次工具调用写不下约 26 KB 以上的文件，而且报错把模型引向原样重试。** 这是第十一轮完整配置场景 3 Task 2"`write_file` 反复报缺少 path 参数"（评 2 分）的原因。链条是：

1. `HKGAIClient.chat()` 不设 `max_tokens`，DeepSeek 在 8192 个输出 token 处结束回复，`finish_reason` 为 `length`；
2. 工具调用的 JSON 断在 `content` 字符串中间，`_arguments()` 把修不好的 JSON 变成 `{}`；
3. `write_file` 拿到空参数，回答"missing required argument: path"；
4. 模型以为是自己漏了参数，原样重发，在同一个位置再被截断。`finish_reason` 存进了 `LLMResponse`，但没有任何代码读它。

用真实模型做了一次调用复现：让模型用一次 `write_file` 写 14 页幻灯片，31.5 秒后返回 `finish_reason: length`、`completion_tokens: 8192`，参数原文 26696 字符、不是合法 JSON，解析结果为空。
第十一轮快速配置成功写出的幻灯片是 26441 字节，刚好在这个上限之下，所以它不是偶发的格式错误：任何稍大的单个文件都会触发。

**4.2 队友写的代码传不回牵头者。** `Router.copy_back` 把队友报告的文件复制进派活人的收件箱，但跳过 `.py` 和 `.sh`（注释："队友自己的工具"）。写报告的团队没有问题，写软件的团队交付的正是 `.py`。
